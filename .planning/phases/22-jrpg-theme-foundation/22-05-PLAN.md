<task type="auto">
  <name>Task 1: Fix contrast violations in glow text and validate token colors</name>
  <files>client/src/styles/retro.css, client/src/styles/tokens.css</files>
  <action>
The highest-risk accessibility issue is the `.retro-text-glow` and `.retro-text-glow-light` classes. These use `color: var(--retro-glow-light)` which is `hsl(var(--hue) 100% 85%)` — an animated hue value. At many hue positions, this color on `#16213e` background fails WCAG AA 4.5:1.

**Fix strategy:** For TEXT elements, use a fixed, pre-validated color instead of the animated hue. Keep the animated glow for non-text decorative elements (box-shadow, border-color, background decorations).

**In retro.css**, update `.retro-text-glow`:
1. Change `color: var(--retro-glow-light)` to `color: var(--jrpg-text-primary)` (#f5f5f5, 12.6:1 contrast)
2. Keep the `text-shadow` using `var(--retro-glow)` — shadow is decorative and exempt from contrast requirements per WCAG 2.1 (text-shadow is not the text color)
3. Keep `-webkit-text-stroke: 1px #000000` — this adds definition and improves readability

**In retro.css**, update `.retro-text-glow-light`:
1. Change `color: var(--retro-glow-light)` to `color: var(--jrpg-text-accent)` (#ffd700, 9.8:1 contrast — gold, still looks themed)
2. Keep the `text-shadow` using `var(--retro-glow)` — decorative

These changes preserve the neon glow VISUAL EFFECT (via text-shadow) while making the actual text color pass contrast. The user sees glowing text that's also readable.

**In tokens.css**, verify and document contrast ratios as CSS comments:
```css
/* WCAG AA Contrast Ratios (against --jrpg-panel-bg #16213e): */
/* --jrpg-text-primary: #f5f5f5 → ~12.6:1 PASS */
/* --jrpg-text-secondary: #b0b0b0 → ~7.2:1 PASS */
/* --jrpg-text-accent: #ffd700 → ~9.8:1 PASS */
/* --jrpg-text-danger: #ff6b6b → ~4.7:1 PASS */
/* --jrpg-text-muted: #808080 → ~4.6:1 PASS (borderline) */
```

If any token value doesn't actually meet the stated ratio when checked manually (ratios in research are approximate), adjust the hex value slightly to ensure it passes. Prefer lightening the text color over darkening the background.

**Also add a minimum font size rule** to tokens.css or retro.css:
```css
/* Enforce minimum font size for Press Start 2P legibility */
.font-jrpg, [style*="Press Start 2P"] {
  font-size: max(var(--jrpg-font-size-min, 12px), 12px);
}
```

This prevents any component from rendering Press Start 2P below 12px, which is the legibility threshold for this bitmap pixel font.

Create or update `e2e/accessibility.spec.ts` to validate WCAG AA contrast ratios using axe-core (already installed as `@axe-core/playwright@4.11.1`).

First check if `e2e/accessibility.spec.ts` already exists (Phase 11 may have created it). If it exists, ADD new test cases — do not replace existing tests. If it doesn't exist, create it.

The test should validate contrast on the landing/marketing page (which uses the JRPG theme and is accessible without WebSocket/game state). This gives us a reliable, deterministic page to test against.

```typescript
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test.describe('JRPG Theme Accessibility', () => {
  test('landing page passes WCAG AA color contrast', async ({ page }) => {
    await page.goto('/');
    await page.waitForLoadState('networkidle');

    const results = await new AxeBuilder({ page })
      .withRules(['color-contrast'])
      .analyze();

    // Log any violations for debugging
    if (results.violations.length > 0) {
      console.log('Contrast violations:', JSON.stringify(results.violations, null, 2));
    }

    expect(results.violations).toEqual([]);
  });

  test('lobby creation page passes WCAG AA color contrast', async ({ page }) => {
    // Navigate to lobby creation (accessible without WebSocket)
    await page.goto('/');
    await page.waitForLoadState('networkidle');

    // Look for the create lobby button/link and navigate
    const createButton = page.locator('text=Create Lobby').or(page.locator('text=New Game')).or(page.locator('[data-testid="create-lobby"]'));

    // Only run if we can reach the lobby creation page
    if (await createButton.isVisible()) {
      await createButton.click();
      await page.waitForLoadState('networkidle');

      const results = await new AxeBuilder({ page })
        .withRules(['color-contrast'])
        .analyze();

      if (results.violations.length > 0) {
        console.log('Lobby creation contrast violations:', JSON.stringify(results.violations, null, 2));
      }

      expect(results.violations).toEqual([]);
    }
  });
});
```

IMPORTANT: axe-core's `color-contrast` rule only works in real browsers (Playwright), NOT in JSDOM (Vitest). That's why this is an E2E test, not a unit test.

If the test discovers violations in the actual rendered page that weren't caught by the manual token review in Task 1, document them as comments in the test file with a TODO for fixing. Do NOT make the test fail on pre-existing violations outside the scope of Phase 22 (e.g., marketing pages using non-token colors). Use axe-core's `exclude` option to skip elements that are outside Phase 22 scope if needed.
