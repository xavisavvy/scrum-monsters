**RED phase first** — write tests in server/domains/AbilityManager.test.ts:

Test categories:
1. **Cooldown validation:**
   - useAbility succeeds when no cooldown active → returns { success: true }
   - useAbility fails when ability on cooldown → returns { success: false, error containing 'cooldown' }
   - Cooldown expires after durationMs → ability usable again (use fake timers)
   - Multiple abilities have independent cooldowns

2. **Mastery tier gating:**
   - useAbility fails when ability not unlocked → returns { success: false, error containing 'not unlocked' }
   - useAbility succeeds when canUseClassAbility returns true

3. **Combat state validation:**
   - useAbility fails when player not in combat (no combatState) → error 'not active'
   - useAbility fails when player combatState !== 'fighting' (downed/ghost) → error
   - useAbility fails when game phase !== 'battle' (passed as param or checked)

4. **Effect application:**
   - Damage ability calls eventBus.emit with 'ability:effect_applied' including damage value
   - Heal ability emits heal effect for lowest-HP target
   - Taunt ability emits taunt effect (massive threat addition)
   - Buff ability emits buff effect with duration
   - Shield ability emits shield effect with power + duration
   - Debuff ability emits debuff effect on boss

5. **Cooldown reset:**
   - resetCooldowns(lobbyId) clears all player cooldowns for that lobby (for new ticket)
   - cleanupLobby(lobbyId) removes all state for lobby

**GREEN phase** — implement server/domains/AbilityManager.ts:

```typescript
export interface AbilityManagerDeps {
  eventBus: ScopedEventBus;
  combatManager: {
    getCombatState: (lobbyId: string) => LobbyCombatState | undefined;
    canUseClassAbility: (lobbyId: string, playerId: string, abilityId: string) => boolean;
  };
  getPlayerClass: (lobbyId: string, playerId: string) => AvatarClass | null;
}
```

State: `Map<lobbyId, Map<playerId, Map<abilityId, CooldownState>>>` where CooldownState = { abilityId, startedAt, durationMs, expiresAt }.

Methods:
- `useAbility(lobbyId, playerId, abilityId)`: validates combat state, mastery unlock, cooldown → applies effect → starts cooldown → emits events → returns { success, error? }
- `isOnCooldown(lobbyId, playerId, abilityId)`: boolean check
- `getRemainingCooldown(lobbyId, playerId, abilityId)`: ms remaining
- `resetCooldowns(lobbyId)`: clear all cooldowns for lobby (new ticket)
- `cleanupLobby(lobbyId)`: remove all state
- `getActiveCooldowns(lobbyId, playerId)`: return all active cooldowns for a player (for client sync)

Private:
- `applyAbilityEffect(lobbyId, playerId, abilityDef)`: switch on effectType, emit appropriate events
- `startCooldown(lobbyId, playerId, abilityId, durationMs)`: set cooldown state

For effect application, emit events via eventBus that will be consumed by the socket handler (Plan 02). Do NOT call CombatManager methods directly for effects — emit events like 'ability:effect_applied' with { lobbyId, playerId, abilityId, effectType, targetType, power, targets }. The socket handler (Plan 02) will translate these into actual game state changes via CombatManager. This keeps AbilityManager focused on cooldown validation and effect declaration.

Exception: For 'damage' effect type on boss, call through to CombatManager since it already handles boss HP reduction and threat. Use `this.deps.combatManager` interface that will be wired with applyAbilityDamageToBoss in Plan 02.

Keep the CombatManager dependency interface minimal — only getCombatState and canUseClassAbility are needed in this plan. Plan 02 will add applyAbilityDamageToBoss and other methods.

Use `vi.useFakeTimers()` in tests to control Date.now() for cooldown expiry testing.
