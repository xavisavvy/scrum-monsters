  <name>Task 1: Provision S3 bucket, IAM user, GHCR auth, and UptimeRobot</name>
  <action>
The following infrastructure must be provisioned manually. Each step is required before deployment can succeed.

**Step A: Create S3 backup bucket with lifecycle policy**

1. Go to AWS S3 Console -> Create bucket
2. Bucket name: `scrummonsters-backups` (or similar unique name)
3. Region: us-east-1 (same as Lightsail)
4. Block all public access: ON (backups should never be public)
5. After creation, go to bucket -> Management -> Lifecycle rules -> Create lifecycle rule:
   - Rule name: `delete-backups-30d`
   - Apply to all objects in bucket (or filter by prefix `scrummonsters/`)
   - Expiration: 30 days
   - Save

**Step B: Create IAM user with restricted S3 access**

1. Go to AWS IAM Console -> Users -> Create user
2. User name: `scrummonsters-backup`
3. No console access needed
4. Attach inline policy (JSON):
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Allow",
         "Action": [
           "s3:PutObject",
           "s3:GetObject",
           "s3:ListBucket"
         ],
         "Resource": [
           "arn:aws:s3:::YOUR_BUCKET_NAME",
           "arn:aws:s3:::YOUR_BUCKET_NAME/*"
         ]
       }
     ]
   }
   ```
5. Create access key (CLI use case) and note the Access Key ID and Secret Access Key

**Step C: Configure VPS .env**

SSH into the VPS and update `/opt/scrummonsters/.env`:

```bash
ssh -i ~/.ssh/lightsail_scrummonsters ubuntu@34.199.135.244
nano /opt/scrummonsters/.env
```

1. Replace `OAUTH_CALLBACK_BASE_URL=https://scrummonsters.com` with `BASE_URL=https://scrummonsters.com`
2. Add `APP_IMAGE_TAG=latest`
3. Add the backup credentials:
   ```
   BACKUP_S3_ACCESS_KEY_ID=<your access key>
   BACKUP_S3_SECRET_ACCESS_KEY=<your secret key>
   BACKUP_S3_BUCKET=<your bucket name>
   ```

**Step D: GHCR authentication on VPS**

On the VPS:

1. Create a GitHub Personal Access Token (classic) at https://github.com/settings/tokens with `read:packages` scope
2. Login to GHCR:
   ```bash
   echo "YOUR_PAT" | docker login ghcr.io -u YOUR_GITHUB_USERNAME --password-stdin
   ```
3. Verify: `docker pull ghcr.io/xavisavvy/scrum-monsters:latest` should succeed

**Step E: Set up UptimeRobot**

1. Create free account at https://uptimerobot.com
2. Add Monitor:
   - Type: HTTP(s)
   - Friendly Name: ScrumMonsters Production
   - URL: `https://scrummonsters.com/api/health`
   - Monitoring Interval: 5 minutes
3. In monitor settings, set **Alert After = 1 failure** (not 2, which is the default -- 2 failures = 10 minutes, exceeding the 5-minute requirement)
4. Add Alert Contact: Type = Email, enter your email address
5. Attach alert contact to the monitor

**Verify HARD-01: Graceful shutdown drains connections (30s, not 10s SIGKILL)**

1. Open https://scrummonsters.com in a browser and confirm the app loads
2. SSH in and stop only the app container, timing it:
   ```bash
   time docker compose -f docker-compose.prod.yml stop app
   ```
3. Expected: The stop takes approximately 2-5 seconds (clean exit after io.close()) or up to 30 seconds under load -- but NOT exactly 10 seconds (which would mean SIGKILL from default grace period)
4. Check app logs for the shutdown sequence:
   ```bash
   docker compose -f docker-compose.prod.yml logs --tail=20 app
   ```
   Expected: "Graceful shutdown initiated" -> "Server closed" (clean exit, not killed)
5. Restart the app: `docker compose -f docker-compose.prod.yml up -d app`

**Verify HARD-02: Backup sidecar connects and can upload**

1. Check that the backup sidecar is running:
   ```bash
   docker compose -f docker-compose.prod.yml ps postgres-backup
   ```
   Expected: Status shows "running"

2. Trigger a manual backup to verify S3 connectivity:
   ```bash
   docker compose -f docker-compose.prod.yml exec postgres-backup sh -c '/backup.sh'
   ```
   Expected: Output shows pg_dump completing and upload to S3 succeeding

3. Verify the backup file exists in S3:
   ```bash
   aws s3 ls s3://YOUR_BUCKET_NAME/scrummonsters/
   ```
   (Or check in AWS S3 Console)
   Expected: A .sql.gz file with today's date

**Verify HARD-03: Rollback works with APP_IMAGE_TAG**

1. Note the current image tag: `docker compose -f docker-compose.prod.yml images app`
2. Find a prior SHA tag from GitHub Packages or: `docker image ls ghcr.io/xavisavvy/scrum-monsters`
3. Test rollback to a specific tag:
   ```bash
   APP_IMAGE_TAG=sha-XXXXXX docker compose -f docker-compose.prod.yml pull app
   APP_IMAGE_TAG=sha-XXXXXX docker compose -f docker-compose.prod.yml up -d --no-deps app
   ```
4. Verify app still works: `curl https://scrummonsters.com/api/health`
5. Roll forward: set APP_IMAGE_TAG back to latest and redeploy
   ```bash
   docker compose -f docker-compose.prod.yml pull app
   docker compose -f docker-compose.prod.yml up -d --no-deps app
   ```

If only one image exists in GHCR (because docker.yml just ran for the first time with sha- prefix), you can skip testing with an alternate tag -- the important thing is that `docker compose pull app` succeeds with the GHCR image and the APP_IMAGE_TAG mechanism works.

**Verify HARD-04: UptimeRobot is monitoring**

1. Go to https://uptimerobot.com dashboard
2. Verify the ScrumMonsters monitor shows status "Up" (green)
3. Confirm monitoring interval is 5 minutes and "Alert After" is set to 1 failure
