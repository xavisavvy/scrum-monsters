# Milestone v1.0: Domain Separation

**Status:** ✅ SHIPPED 2026-02-02
**Phases:** 1-6
**Total Plans:** 30

## Overview

Refactor a 2000+ line monolithic GameStateManager into separate Session, Estimation, and Combat domains to improve maintainability while preserving real-time multiplayer performance. The journey follows dependency order: establish type definitions and communication infrastructure first, extract domain managers sequentially (Session -> Estimation -> Combat), optimize with fine-grained events, and finally implement the new estimation-before-battle game flow.

## Milestone Summary

**Decimal Phases:**
None in v1.0

**Key Decisions:**

- Map types for runtime state — Use Map<string, T> for player collections
- Event naming convention — domain:action format (e.g., estimation:vote_cast)
- Scoped subscription pattern — Use subscribeScoped(lobbyId, event, listener)
- Clean slate on Lobby type — Proper domain separation requires redesigning core type
- Fine-grained events — Real-time game best practice, send only what changed
- Three domains (Session/Estimation/Combat) — Natural boundaries based on concerns
- Estimation before battle entry — Keep voting focused, combat as waiting entertainment

**Issues Resolved:**

- 2000+ line monolith split into maintainable domain managers
- Full-state broadcasts replaced with fine-grained events
- Memory leak prevention via ScopedEventBus cleanup contracts
- Cross-domain coordination via EventBus subscriptions

**Issues Deferred:**

- Full removal of lobby_updated (16 documented emissions remain as fallback)
- Orphaned shared/types/ files (SessionState, EstimationState, CombatState not imported)
- Phase 5 missing formal VERIFICATION.md (functionality verified in summary)

**Technical Debt Incurred:**

- ARCH-07, ARCH-08, INTG-01 partially complete (fallback pattern intentional)
- Some legacy gameState patterns remain in socket handlers
